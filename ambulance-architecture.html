Ambulance / Service Booking App

Architecture & Technical Overview
Version 1.0 | Prepared: 2026-08-30
Based on: Direct codebase inspection — Laravel 10 (PHP 8.2) monolithic application

1. Purpose

This document describes the current, as-built technical architecture of the platform, covering both product lines it serves:

  • Vehicle Booking (Taxi/Ride-hailing) — Rider requests a ride, a Driver is dispatched, ride is completed and paid for.
  • Service Booking (Home/Field Services) — Rider books a service (e.g. ambulance, medical support, field services), a qualified Driver/Service Provider is dispatched, service is delivered and paid for.

It is meant to give stakeholders an accurate picture of what exists today, so that scoping, estimation, and roadmap discussions are based on facts rather than assumptions.

2. System Summary

The backend is a single Laravel 10 (PHP 8.2) monolithic application — not a microservices architecture. It serves three kinds of clients from one codebase:

Client Interface Location
Rider mobile app REST API (/api/rider/*) External; mobile source not in this repository
Driver mobile app REST API (/api/driver/*) External; mobile source not in this repository
Admin / Company staff Server-rendered web dashboards (Blade) Part of this repository

The system is multi-tenant: each customer/partner company is identified by subdomain ({company}.), enforced via an IdentifyTenant middleware on every tenant-scoped route.

4. The Two Booking Domains

Both domains share the same auth, tenant, notification, and payment infrastructure. They differ in what is being fulfilled: a ride vs. a service order.

4.1 Vehicle (Taxi) Booking — Dispatch Flow

sequenceDiagram participant Rider as Rider App participant API as Rider API participant Job as FindDriverJob participant Redis as Redis participant WS as WebSocket participant DriverApp as Driver App Rider->>API: Request ride API->>Job: Dispatch FindDriverJob Job->>Redis: Start search (0-2km) Job->>WS: broadcast (searching) Note over Job: Wait 30s for acceptance Job->>Job: Expand to 2-5km Job->>WS: broadcast (expanding_search) Job->>Job: Expand to 5-10km DriverApp->>API: POST Accept API->>Redis: Acquire lock booking:accept:{rideID} alt Already taken API->>WS: reject this driver else First valid API->>WS: broadcast driver_assigned end

Key implementation facts:

  • Radius expansion: 0–2km → 2–5km → 5–10km, each stage waits up to 30 seconds
  • Concurrent-acceptance race resolved with Redis lock (booking:accept:{rideID})
  • All progress pushed over WebSocket channel private-rider-driver-finding-{rideID}

4.2 Service Booking — Order Flow

sequenceDiagram participant Rider as Rider App participant API as Rider API participant DB as MariaDB participant Job as FindNearbyServiceDriversJob participant WS as WebSocket participant DriverApp as Driver App participant Stripe as Stripe Rider->>API: Browse/cart → POST /orders API->>DB: Create order (searching) API->>Job: Dispatch search job Job->>WS: notify nearby drivers DriverApp->>API: POST accept API->>DB: Assign driver DriverApp->>API: POST start API->>DB: Generate start OTP API->>WS: broadcast OTP to rider Rider->>DriverApp: Verify OTP verbally DriverApp->>API: POST verify-start-otp DriverApp->>API: POST complete API->>DB: Generate completion OTP DriverApp->>API: POST verify-complete-otp DriverApp->>API: POST payment alt Cash API->>DB: status: done else Online API->>Stripe: Create PaymentIntent Rider->>Stripe: Confirm payment Stripe->>API: Webhook API->>DB: status: done end

Additional capability: Drivers can register additional services on-site (/driver/service-orders/{id}/additional-services), each with OTP verification.

5. Application Services — Module Breakdown

The Laravel monolith is organized by role under app/Http/Controllers/:

Module Path Scope
Rider API Api/Rider/ Cart, orders, addresses, payments, scheduled rides, vehicle types
Driver API Api/Driver/ Online/offline, KYC, documents, bank accounts, service orders, vehicle, withdrawals
Common API Api/Common/ Auth, OTP, profile, address, categories, acceptance
Company (Partner Admin) Company/ Driver/rider management, KYC, pricing, analytics, payments, reports (~50 controllers)
Operator Operator/ Scoped version: drivers, riders, scheduled rides (no tenant-wide config)
SysAdmin SysAdmin/ Platform-wide administration, tenant management, mirrors Company controllers

This is a role-partitioned monolith, not domain microservices: all roles are controller namespaces inside one deployable app, sharing one database.

12. General Platform Presentation & Functional Descriptions

Platform capabilities described in functional/product terms — what each user type can actually do — independent of implementation.

12.1 Platform Overview

The platform is a multi-tenant SaaS system: each partner company operates its own branded instance (own subdomain, drivers, service catalog, pricing) on shared infrastructure. Within each tenant, two booking businesses run side by side:

  • Vehicle Booking — on-demand taxi/ride-hailing service
  • Service Booking — on-demand home/field-service marketplace (e.g. plumbing, electrical, ambulance, medical support)

Five distinct actor types: Rider, Driver/Service Provider, Company (Partner) Admin, Operator, Platform SysAdmin.

12.2 Rider — Functional Capabilities

  • Register and log in (email/mobile + password); verify via email and SMS OTP
  • Manage profile, saved addresses, profile photo
  • Browse available vehicle types and facilities (AC, luggage capacity)
  • Browse service categories, subcategories, and services
  • Get instant distance-and-fare estimate before booking
  • Request ride and track search in real time (progressive radius expansion with live updates)
  • Add services to cart, adjust quantities, check out as order
  • Track ride/order lifecycle in real time (searching → assigned → in progress → completed)
  • Schedule rides in advance; view or cancel scheduled rides
  • Verify service start and completion using driver-entered OTP codes
  • Pay by cash or card (Stripe)
  • Leave reviews; raise complaints
  • View rider credit/wallet balance and history

12.3 Driver / Service Provider — Functional Capabilities

  • Register, log in, password-reset independent of rider
  • Go online/offline; send periodic heartbeat/location updates
  • Complete KYC: upload identity/license documents; track approval and expiry
  • Register one or more vehicles; link bank account for payouts
  • Set which service categories/subcategories they are qualified for
  • Receive and accept/decline ride and service-order requests as dispatched
  • Update ride status through trip lifecycle (arrived, started, completed)
  • For service orders: start (generate rider OTP), complete (generate second OTP), register additional on-site services (independently OTP-verified)
  • Select payment method (cash or online) at end of ride/order
  • View and manage schedules and appointments
  • Request withdrawals of accumulated earnings
  • View reviews; file and track complaints

12.4 Company (Partner) Admin — Functional Capabilities

Run one tenant's entire operation from a web dashboard:

  • Manage driver roster: onboarding, KYC approval, document/license expiry tracking, vehicle assignment, bank details, service-category mapping
  • Manage rider base: profiles, addresses, credits/wallet adjustments, complaint handling
  • Define service catalog: categories, subcategories, services, facility items
  • Configure pricing: vehicle pricing, service pricing (state-wise)
  • Configure operating geography: zones, neighborhoods, state-level settings
  • Configure tax rules and payment settings
  • Review and moderate driver and rider reviews and complaints
  • Track and manage scheduled rides across driver fleet
  • Send push notifications (individual or by group); manage notification group membership
  • Customize email templates for tenant communications
  • View operational analytics: revenue trends, ride-status breakdowns, insights map, assigned-vs-missed, completed-vs-canceled
  • Generate and export reports (Excel/PDF)
  • Manage payments and driver withdrawal requests
  • Manage operator accounts working under them

12.5 Operator — Functional Capabilities

Scoped-down version of Company Admin for day-to-day staff:

  • Manage drivers, driver vehicles, riders, rider credits, scheduled rides
  • NO access to tenant-wide configuration (pricing, taxes, zones, categories)

12.6 Platform SysAdmin — Functional Capabilities

Operate above all tenants; mirror nearly every Company Admin capability at platform scope:

  • Onboard and manage companies/tenants (customers of platform)
  • Perform driver, rider, KYC, complaint, review, pricing, zone, tax, notification management across any tenant
  • Manage platform-wide payments and bank lists
  • View platform-wide analytics and reports

12.7 Shared, Cross-Cutting Functionality

  • Real-time updates over WebSocket for ride search, order status, driver location/heartbeat
  • Push notifications (Firebase Cloud Messaging)
  • Stripe-based online payments alongside cash
  • Multi-tenant isolation — every tenant's data, drivers, riders scoped to that tenant's subdomain only

13.3 TLS / Certificate Scope

  • Certificate is single-domain: CN=amb.zcodia.in, no wildcard or additional SANs
  • WebSockets server (port 6001) DOES terminate TLS explicitly (websockets:serve --ssl)
  • Main application (port 8000) DOES NOT — runs php artisan serve with no SSL flag. HTTPS for API/admin routes is handled by an external reverse proxy/load balancer (NOT PRESENT in this repo)
  • Multi-tenant routing pattern ({company}.) requires wildcard subdomain resolution. Certificate is single-domain — production wildcard/multi-SAN certificate coverage should be confirmed separately

13.4 DNS & Multi-Tenant Domain Routing

  • Each tenant accessed via {company}.amb.zcodia.in (or equivalent domain)
  • IdentifyTenant middleware extracts company subdomain and scopes all queries to that tenant
  • For production: wildcard DNS record (*.amb.zcodia.in) should point to the host; wildcard TLS certificate should cover all subdomains

13.5 Internal Service Communication Paths

  • API → Database: Direct SQL queries via Laravel's database layer (PDO/MySQL wire protocol on port 3306)
  • API → Redis: Cache queries, queue job dispatch, distributed locking (port 6379)
  • API → WebSocket server: Broadcasting via pusher channel (configured to connect to same host on port 6001)
  • Queue workers: Read jobs from Redis; fetch job-specific data from database; may publish events to WebSocket

13.6 External Third-Party Dependencies

Service Purpose API Calls

Google Maps Distance Matrix (ride fare estimation), Geocoding (address lookup) Outbound (API)
Firebase Cloud Messaging Push notifications to rider/driver apps Outbound (API)
Mail Provider Email delivery (Mailgun / Postmark / SES configured as options) Outbound (SMTP or API)

13.7 Queue and Asynchronous Processing

  • Job dispatcher: API routes dispatch jobs into Redis queue
  • Queue worker: Separate Laravel process (or containerized) runs php artisan queue:work, consuming jobs from Redis
  • Example jobs: FindDriverJob (search for drivers), SendRiderScheduleNotification (scheduled ride reminders), PushNotification (broadcast messages), GenerateReport (export Excel/PDF)

13.8 CORS Policy Configuration

  • Configured in config/cors.php (Laravel default)
  • Mobile apps and web admin are same-origin as backend (via subdomain or internal network), so CORS is typically permissive or not strictly enforced
  • Third-party integrations (if any) would need explicit allowed origins

13.9 Authentication Token Flow

  • Registration: Rider / Driver POST to /api/{rider|driver}/register, receives bearer token
  • Login: POST to /api/{rider|driver}/login, returns bearer token
  • Bearer token in requests: Mobile apps send Authorization: Bearer {token} header on all protected endpoints
  • Token storage: Stored in Laravel's personal_access_tokens table (encrypted in database)
  • Token expiry: Not explicitly configured in codebase — Laravel Sanctum tokens are persistent by default unless revoked or cleared

13.10 Equipment and Hosting Specifications

  • Host VM specs: Not documented in repo; assumed to be a single Linux VM (possibly AWS EC2, DigitalOcean, Linode, or on-prem)
  • Containerization: All services run inside Docker containers orchestrated by Docker Compose
  • PHP container: PHP 8.2-FPM base, with Laravel application code mounted as volume
  • Database container: MariaDB 11.4 with persistent volume for data storage
  • Redis container: redis:7-alpine with 256MB memory limit (configured in docker-compose.yml)
  • WebSocket container: Separate PHP 8.2-FPM instance running artisan websockets:serve
  • Scaling: No orchestration — to scale, would need manual Docker Compose expansion or migration to Kubernetes

13.11 Compliance and Data Processing

  • Data residency: Not documented; data is stored in MariaDB on the host VM, location depends on where VM is hosted
  • Encryption at rest: Depends on host VM's storage setup; not configured at database level in this repo
  • Encryption in transit: TLS on port 6001 (WebSocket); port 8000 (app) depends on external reverse proxy (NOT PRESENT in repo); internal Docker communication is unencrypted
  • PII handling: Rider/driver personal data (name, phone, address, KYC documents) are stored in database; no explicit PII anonymization or retention policies documented
  • Payment data: Stripe handles payment processing; application does not store card details (PCI compliance is Stripe's responsibility)

14. Production Hosting Best Practices (Recommendations)

Concern Recommendation
Reverse Proxy / Load Balancer Place an nginx, HAProxy, or cloud load balancer (AWS ALB/NLB) in front of port 8000; terminate HTTPS there; route to app container.
TLS Certificates Use wildcard certificate covering *.amb.zcodia.in for multi-tenant support. Automate renewal with Let's Encrypt / certbot.
Database Backup & Recovery Automated daily backups (mysqldump or snapshots); test restore procedure; keep backups off-site.
Redis Persistence Enable RDB snapshots or AOF (Append-Only File) for Redis; consider separate Redis instance for cache vs. queue for fault isolation.
Monitoring & Alerting Deploy APM (e.g. New Relic, Datadog, Sentry); set up alerts for high error rates, response time degradation, and infrastructure health.
Logging Aggregation Ship application and container logs to centralized logging (e.g. ELK, Splunk, CloudWatch); enable log rotation locally to avoid disk filling.
Database Indexing & Query Optimization Profile queries; ensure key indices exist on foreign keys, timestamps, and search columns (e.g. driver_id, ride_id, created_at).
Container Registry & CI/CD Build and push images to a private registry (Docker Hub, ECR, etc.); automate deployment via CI/CD pipeline (GitHub Actions, GitLab CI, Jenkins).
Environment Secrets Management Use a secrets management tool (HashiCorp Vault, AWS Secrets Manager, etc.) instead of .env files in version control.
Auto-Scaling & Failover Consider container orchestration (Kubernetes, ECS) if anticipating high traffic spikes or requiring multi-region failover.

15. Cybersecurity & Role-Based Access Control (RBAC)

15.1 RBAC Implementation

The platform enforces five distinct roles, each with dedicated middleware and route scoping:

Role Middleware Class Route Namespace Capabilities
Rider RiderApiMiddleware /api/rider/ Request rides, order services, view history, manage addresses, pay orders
Driver DriverApiMiddleware /api/driver/ Accept/decline rides, update ride status, manage documents, request withdrawals
Company Admin CompanyMiddleware /company/ Manage drivers/riders, configure pricing/zones, view analytics, process payments
Operator OperatorMiddleware /operator/ Manage drivers/riders/scheduled rides (no tenant-wide config)
Platform SysAdmin SystemAdminMiddleware /sysadmin/ Onboard tenants, manage across all tenants, platform-wide analytics

15.2 Enforcement Mechanisms

  • Middleware guard: Each role's middleware checks the authenticated user's role and grants or denies access to that role's routes
  • Tenant isolation: IdentifyTenant middleware resolves tenant from subdomain; all queries are scoped to that tenant's ID
  • Resource authorization: Controller methods verify that the authenticated user owns/is associated with the resource being accessed (e.g. a rider can only view their own addresses)
  • Token-based auth: All API endpoints (except public endpoints like login) require a valid bearer token; token is validated by auth:sanctum middleware

16. Disaster Recovery Plan

Critical Risk Statement: The current single-host Docker Compose deployment has no automated failover, no replica database, and no multi-region backup. If the host VM fails, the entire platform goes offline until the host is recovered or replaced. This is acceptable for development and early staging, but not suitable for production serving real users.

16.1 Recommended DR Best Practices

# Practice Benefit
1 Automated daily database backups to off-site object storage (AWS S3, Google Cloud Storage) Data recovery in case of database corruption or deletion; meet RTO/RPO targets
2 Test database restore procedure quarterly Confirm backups are valid and restore can complete within RTO window
3 Database replication (MariaDB primary-replica) or managed database service (AWS RDS, Google Cloud SQL) Automatic failover to replica if primary fails; zero data loss
4 Redis persistence (RDB snapshots or AOF); back up snapshots off-site Recovery of in-flight jobs, locks, and cache state after restart
5 Multi-region or multi-AZ deployment (e.g. AWS ECS on multiple AZs, or Kubernetes across regions) Survive host/AZ/region failure; automatic failover; no manual intervention
6 Container image versioning and registry; rollback procedure documented Quick rollback to previous stable version if deployment introduces a bug
7 Runbook for manual failover (standby host, data restore, DNS switch) Structured response in an emergency; reduces time to recovery
8 Monitoring and alerting on database replication lag, backup success/failure, host health Early warning if DR infrastructure is degraded; time to fix before actual failure
9 Document RTO (Recovery Time Objective) and RPO (Recovery Point Objective) targets; track compliance Align infrastructure investment with business continuity requirements
10 Quarterly DR drill: simulate failure, execute recovery, verify services are online and data is consistent Catch gaps in runbooks, train operations team, build confidence in recovery procedure

16.2 Immediate Actions (Before Production Release)

  • Establish backup strategy: Daily automated database backups to off-site storage; test restore at least once
  • Enable debug mode off: Verify APP_DEBUG=false in production .env
  • Enable HTTPS for API: Place a reverse proxy (nginx/HAProxy) with wildcard TLS certificate in front of port 8000
  • Document & review: Capture how the production host is set up; document steps to rebuild it from scratch
  • Plan scaling: If expecting significant traffic growth, prototype migration to Kubernetes or managed container service
